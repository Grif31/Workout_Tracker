# Feature and data-model reference

Detail moved out of CLAUDE.md to keep it short. CLAUDE.md keeps the rules; this file keeps how each feature works. Read the section for the feature you're touching.

## Dependency upgrades

### Frontend (Expo SDK)
```
SDK upgrades: `npx expo install expo@^N --fix` can fail with ERESOLVE, because it updates dependencies and
devDependencies in two separate npm runs and the not-yet-updated jest-expo pins the old @react-native/jest-preset.
Write the versions `expo install --check` lists into package.json and run one `npm install` instead.
@react-native/jest-preset is a required peer of jest-expo and must match react-native exactly; bump them together.
Before pushing, prove EAS can install: `npm_config_legacy_peer_deps=false npm ci` (only the development profile sets legacy peer deps)
In PowerShell: `$env:npm_config_legacy_peer_deps = 'false'; npm ci; Remove-Item Env:npm_config_legacy_peer_deps`
Pass = "added N packages" with no ERESOLVE. Ignore the deprecation and `npm audit` noise; never `npm audit fix --force` (it breaks Expo's pinned versions)
```

### Backend (pip)
```
requirements.txt pins every version (direct and transitive) and src/.python-version pins Python 3.13, so tests run the versions Nixpacks deploys.
Upgrade by bumping pins, installing into a fresh venv, running the suite, then refreezing the transitive section.
colorama/tzdata carry Windows-only markers; keep them, or Linux installs pick up packages they don't need
```

## Data model and features

- **PR types (cardio):** `best_time` (`weight_context` = distance milestone in km) and `best_distance` (`weight_context` = duration milestone in minutes). Rides (template name matching `isCycling` / `is_cycling`) use `CYCLING_*_MILESTONES` (5K to 100 Mile, up to 2 hr), everything else the running list; `cardio_milestones()` in `endurance_standards.py` picks, by the template's name. Rides also hold `longest_distance` (Longest Ride, km) and `max_elevation` (Most Elevation, metres, shown in ft beside miles), one each per exercise at `weight_context` -1 like `max_duration`
- **PR history:** `PersonalRecord` rows are upserted in place (current bests only). `PREvent` is the append-only history — one row per PR moment with `previous_value` and `workout_id`; written by every upsert branch in `workout_routes.py` and rebuilt by `_recompute_prs_for_templates`'s chronological replay on workout edit/delete. `improved_by` is sign-normalized (positive = better; `best_time` improves downward). Backfill for pre-existing data: `flask backfill-pr-events --apply`.
- **Cardio sets** have: `cardio_duration` (minutes), `distance`, `distance_unit` ('km'|'mi'), `intensity` (pace in the set's own unit, min per km or mi, rides included; display converts to speed), and from GPS `elevation_gain` (m) and `max_speed` (km/h). With auto-pause a GPS set's `cardio_duration` is moving time and `Workout.duration` the time out, stops included
- **GPS cardio exercises** also store: `route_polyline` (encoded Google polyline string), decoded with `@mapbox/polyline`
- **GPS best efforts:** `cardio_best_efforts` rows hang off an `Exercise` — the fastest window covering each distance milestone and the furthest reached inside each duration milestone, scanned on the phone at save time by `utils/bestEfforts.ts` and sent as the exercise payload's `best_efforts`. `_compute_and_upsert_cardio_prs` treats each as one more bout, so a measured 5K beats the whole-run extrapolation through the upsert that already keeps the best. They are **stored** rather than recomputed for two reasons: `route_polyline` encodes latitude/longitude only, so per-point timing is gone after the save (no backfill is possible for runs recorded before this shipped), and `_recompute_prs_for_templates` rebuilds PRs from what sits on the Exercise — an effort that lived only in the request would be wiped by the next edit of any workout for that exercise. Editing a GPS run's distance or duration by hand clears its efforts, since the user is saying the trace was wrong. The milestone floats are mirrored in `constants/cardioMilestones.ts` and a test fails if the two lists drift
- **Bodyweight volume:** for `Bodyweight`/`Weighted` equipment, volume adds the user's bodyweight-at-the-time scaled by `ExerciseTemplate.bodyweight_load_factor` (fraction of bodyweight the movement shifts — push-up ~0.6, sit-up ~0.35, pull-up ~1.0; `NULL` → 1.0). All volume math goes through `compute_effective_weight(weight, equipment, bodyweight, load_factor)` in `utils/volume.py`. New library/custom exercises get a factor from the name heuristic `derive_bodyweight_load_factor`. After adding the column or retuning any factor, run `flask backfill-workout-volume --apply` to recompute stored `Workout.volume`. Never use effective weight for PR/strength-score logic — those read raw `Set.weight`.
- **Weight units:** per user — `user.weight_unit` is `'kg'` or `'lbs'`; delta: kg=2.5, lbs=5. Stored set weights, PR values (both `personal_records` and `pr_events`, incl. `previous_value`), and bodyweight logs are always in the user's *current* unit — switching units bulk-converts them (`_convert_stored_weights` in `user_routes.py`). Exception: `Workout.volume` is always lbs. A stats endpoint that reports a volume total next to `weight_unit` (progress buckets, weekly summary and its history, profile lifetime volume) converts it with `volume_in_user_unit` in `utils/volume.py`; summing `Workout.volume` raw shows kg users pounds labelled kg. The workout POST's `total_volume` stays lbs, and the app converts it (`toExactVolume`). Body measurements (`body_measurements`) have no unit column: they follow the weight unit (lbs → inches, kg → cm, `lengthUnitFor` in `utils/bodyMetrics.ts`) and `_convert_stored_weights` converts them ×/÷2.54 to the tenth on a switch.
- **Heart rate:** `Workout.avg_heart_rate` / `max_heart_rate`, integer bpm, nullable. Read from Apple Health after the workout POST succeeds and attached via PATCH (`utils/heartRateSync.ts`) — never folded into the POST, because a native HealthKit query must not delay a save. NULL is meaningful: it means no wearable or sync off, so never default these to 0. Aggregation lives in `utils/heartRate.ts`, which imports nothing native and so is unit-testable on any platform; it drops samples outside 20-260 bpm, mirroring the `validate.Range` in `schemas.py`. Any wearable that writes to Apple Health works (Apple Watch, chest strap, Whoop) — there is no watchOS target and no `WCSession`
- **`starter` flag:** `Routine.starter` / `WorkoutTemplate.starter` mark what onboarding generated (`POST /api/ai/save` with `starter: true`, which also flags each day's template). The free 7-template / 2-routine caps (client-side, `CoachScreen`) skip them, so nobody hits a wall on day one. Saving one also sets `User.starter_granted`, which is never cleared: a free account's one onboarding program (`free_onboarding_allowed`, routines only) doesn't come back by deleting the routine.
- **Weekly review:** `POST /api/ai/weekly-review` returns `went_well` / `lagged` / `next_change` from `_build_insights_context`. The app sends the summary week's Monday as `week_start`, and the context is read `as_of` that week's end (every query bounded, so nothing after the week leaks in); without `week_start` it reads the rolling last 7 days like insights. Parts citing a lift or numbers the Coach wasn't given are dropped by `_is_grounded`, shared with insights, so fewer than three can come back. JSON key order isn't preserved (Flask sorts it): the app lays the parts out itself. Free-vs-premium is client-side until server premium (TODO §21 Phase 4).
- **Insight feedback:** each insight card has helpful / not helpful thumbs (`CoachScreen`, optimistic, reverted on failure; the vote also rides in `coach_insights_cache`). A thumbs down offers optional reason chips (`reason`: `known` / `irrelevant` / `wrong` / `vague`, `INSIGHT_FEEDBACK_REASONS` in `schemas.py`; dropped on a helpful vote). `POST /api/ai/insights/feedback` stores the vote in `insight_feedback` keyed by the insight's title and body, since insights themselves aren't stored; a repeat vote replaces it and `helpful: null` deletes it. `/api/ai/insights` quotes the last 20 votes from 90 days into its prompt (type, title, reason) and tells the Coach to lean toward the helpful kind without dropping MRV or fatigue flags; it returns `shaped_by_feedback` (the app shows "Shaped by your feedback") and attaches the stored `helpful`/`reason` to any insight that comes back word for word, so its thumb stays filled. The weekly review prompt doesn't read them.
- **Server-side premium (`utils/premium.py`, `routes/premium_routes.py`):** `User.is_premium` is written only by the RevenueCat webhook (`POST /api/webhooks/revenuecat`, authenticated by `REVENUECAT_WEBHOOK_SECRET` in the Authorization header; a cancellation keeps access to the period's end, a refund or expiry revokes) by `POST /api/premium/sync`, which asks RevenueCat's REST API (`REVENUECAT_SECRET_KEY`) and is what counts promotional grants, and by "Sync everyone from RevenueCat" on `/admin/system`, which makes the same call for every account. The app calls sync whenever its own Premium answer changes (`utils/premiumSync.ts`), so an account whose answer never changed (beta testers granted before 2026-10-13, when neither the webhook nor the sync existed) stays `is_premium = false` until "Sync everyone" runs. **`PREMIUM_ENFORCED=true` turns the refusals on; unset, `has_premium()` is True for everyone**, so shipping the code changes nothing until it is flipped. Enforced: `/api/ai/insights` is premium only (402 `premium_required`); `/api/ai/generate` and `/api/ai/save` are premium except that a free account may generate and save its onboarding routine (`starter: true`) until it has one, at 3 generations a day instead of 10; `/api/ai/weekly-review` gives a free account the first part and names the rest in `locked`. The stats routes (muscle volume, density, progress rate, alternatives, scores) are not gated on purpose: the app shows a free account its own numbers blurred behind a lock, and they cost nothing to compute. Turn-on checklist (live on `/admin/system`): set the RevenueCat env vars on Railway, run `flask grant-beta-premium --apply` for beta testers, press "Sync everyone from RevenueCat" there until a run finishes with nobody unanswered (otherwise enforcement refuses testers whose flag was never written), then set `PREMIUM_ENFORCED=true`.
- **Premium analytics (client-gated, see above):** `/api/stats/muscle-volume` also returns `session_count`, `weekly_history` (the 4 weeks before, oldest first), `this_week_total` (raw sets) and `last_week_to_date_total` (last week up to the same weekday, so a partial week isn't compared with a whole one); `/api/stats/progress` buckets carry `density` (volume per timed minute, user's unit) and `metrics_logged.density`; `/api/stats/pr-velocity` fits a line through each lift's best estimated 1RM per workout over 12 weeks (`utils/pr_velocity.py`: plateau = flat over the last 8 weeks, never claimed before the data spans them); `/api/exercises/<id>/alternatives` ranks same-muscle, other-equipment swaps and drops what loads a flagged injury by name (`utils/exercise_alternatives.py`). `/api/stats/exercise/last-session` sets carry `rpe` for the in-workout next-session target (`utils/overloadTarget.ts`, rules not AI).
- **Paywall funnel:** `paywall_events` (one row per step: `upsell_shown`, `paywall_viewed`, `plan_selected`, `purchase_started`, `purchase` and `restore` with their `outcome`), posted fire-and-forget by `utils/paywallEvents.ts` from `PaywallScreen` and `PremiumTeaser` to `POST /api/paywall/events`, read by `/admin/paywall`. Every event carries the paywall `source`, so a purchase is credited to what opened the paywall; the page counts people, not events. A new paywall entry point needs only a new `source` (and a label in `PAYWALL_SOURCE_LABELS`, `utils/admin_stats.py`). It's the only behavioural data the app records, and the privacy policy's Usage data paragraph says so: anything else tracked needs that paragraph and the App Store privacy answers changed first
- **Achievements (`utils/achievements.py`, `routes/achievement_routes.py`):** `user_achievements` rows are kept once earned: nothing deletes one except account deletion, and `evaluate_achievements` only inserts. It replays the user's whole history so each badge is dated by the workout that crossed it; the check after a workout POST/PUT and `flask backfill-achievements` share it. Keys name the rung (`volume_6`), never a value, so unit ladders need no `_convert_stored_weights` entry. Free for everyone (no `has_premium()`), and `GET /api/achievements` never sends an unearned hidden badge's key or name
- **Profile's displayed PRs:** `profile_pr_pins` (up to 3, by exercise + `pr_type` + `weight_context`, not `personal_records.id`, which edits rebuild) via `GET`/`PUT /api/personal-records/pins`. `User.pr_pins_saved` tells "chose none" from "never chose", which shows defaults from `defaultPins` in `utils/profilePins.ts`. GET leaves out a pin whose PR is gone. A max_reps pin's `weight_context` is a weight, so `_convert_stored_weights` converts it
- **Scores:** Strength Score (lift percentiles vs bodyweight) and Endurance Score (running pace percentiles, best-within-tier: core 5K+ 70% / speed 400m-1mi 30%) share the `STRENGTH_TIERS` percentile tiers and both write to `strength_score_snapshots`, separated by `score_type` (`'strength'` | `'endurance'`) — every snapshot read must filter on it. They also share their hero ring (`components/ScoreRing.tsx`) and percentile bars (`components/PercentileBar.tsx`), since the two screens are meant to read as one screen for two metrics — a presentation change belongs in those components, never in one screen. Neither score adds Greek Rank points; the higher one only gates the top two ranks (see Greek Rank below)
- **Greek Rank Volume (30%)** is weekly training load, not workout count (Consistency and Dedication already count workouts): working sets (warm-ups and rows with no reps excluded; a timed-hold set counts as 1) plus cardio minutes / 3, capped at 40 per workout, averaged over 8 weeks, scored by `compute_training_load_score` in `utils/strength_standards.py`
- **Greek Rank:** the score is effort only, `consistency*0.40 + dedication*0.30 + volume*0.30` (`compute_greek_score`), so every user gets a rank with no gender or bodyweight. Titan also needs the higher of the Strength/Endurance Scores at >= 50th percentile and Aretē >= 80th (`GREEK_RANK_PERFORMANCE_GATES`, applied by `apply_greek_rank_gates`); a user who misses a gate is held one rank below it. Read the rank from `GET /api/stats/greek-rank` (no gender required, returns `next_gate`, `gates`, `held_by_gate`, `profile_missing`) via `_greek_rank_data()` in `strength_score_routes.py`. `strength-score` still returns `greek_rank`/`greek_score`/`greek_score_components` from the same helper only for app builds 1.1.6 and earlier; new code must not read the rank from there, since it returns 422 without gender. Frame unlocks and rank-circle state follow the rank held, never the raw score, because a gated score can sit inside a band the user hasn't unlocked

## Production env vars

- **Backend env vars (Railway):** `DATABASE_URL`, `JWT_SECRET_KEY`, `APPLE_BUNDLE_ID` (comma-separated: Apple sets a token's audience to the requesting app's bundle ID, so it lists `com.aretefitness.app` and the dev build's `com.aretefitness.app.dev`), `ADMIN_PASSWORD` (admin pages), `RAPIDAPI_KEY` (ExerciseDB image suggest), mail/SMTP creds, `REVENUECAT_WEBHOOK_SECRET` + `REVENUECAT_SECRET_KEY` (server-side premium) and `PREMIUM_ENFORCED` (off until the checklist under Server-side premium is done), `AI_DAILY_BUDGET_USD` (optional, default 20: estimated dollars all users together may spend on the AI routes per day, summed from `ai_call_log`; past it they answer 503 `budget_spent` without calling the model), `SENTRY_DSN` (optional: backend error reporting, off when unset; events come from any `logger.error`/`.exception`, since the catch-all errorhandler hides 500s from the Flask integration)
